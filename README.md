# FocusBubble

An offline Expo SDK 58 application for personal goals, roadmaps and focus sessions, with a local Kotlin Android overlay module. No account or backend.

## Run

Use Node 22.13+ and npm. Dependencies are selected with Expo’s SDK compatibility map.

```sh
npm install
npx expo install --check
npm run typecheck
npm run lint
npm test
npx expo start --dev-client
```

Five tabs: Today, My goals, Focus, Progress and Settings. On first launch, onboarding leads into the goal wizard. Create a real goal; the database starts empty. SQLite saves goals, roadmaps, preferences and sessions locally. Export JSON backups in Settings before uninstalling or clearing app data.

## Android development build

For standalone APK downloads through GitHub Releases, follow [GitHub and Expo release setup](docs/GITHUB_RELEASE_SETUP.md). The included workflow builds on EAS and attaches the APK to a testing prerelease.

The overlay is a real `TYPE_APPLICATION_OVERLAY` window, not an in-app button. It requires an Android development build. Expo Go can only run the ordinary application features.

```sh
npx eas-cli@latest login
npx eas-cli@latest build:configure
npx eas-cli@latest build --platform android --profile development
```

These commands require your own Expo account and project association. Install the resulting APK on a physical Android device. Start Metro with `npx expo start --dev-client`, then connect the development client. For local builds, install the Android SDK and the JDK required by SDK 58, then run `npx expo run:android --device`. Native application directories are generated by Expo; make native changes under `modules/focus-bubble`, never in generated directories.

Expo autolinks local modules in `modules/`. `expo-module.config.json` registers `FocusBubbleModule`. The library manifest merges overlay and foreground-service declarations. Check autolinking with `npx expo-modules-autolinking resolve --platform android` before building.

If a client reports `Cannot find native module 'ExpoTopicSubscriptionModule'`, its native notifications implementation does not match the installed JavaScript package. FocusBubble checks this capability before loading notifications so goals and timers can still open. Notification opt-in explains when a newer development build is required. Rebuild and reinstall the development client after native dependency changes; restarting Metro alone cannot add a native module. Router “missing default export” warnings alongside this error are secondary to the failed module import.

Start a session, open **Keep your goal in sight**, read the explanation, then explicitly open Android’s overlay settings. Grant permission, return and enable the bubble. Notification permission is separate and optional in Settings. Drag the bubble, tap to expand, double tap to pause/resume (configurable), or hold and release to open additional controls. Drop at the bottom to hide without finishing. Enable again from the bubble screen to restore a hidden bubble.

## Architecture

- `src/app`: Expo Router routes only.
- `src/components`: shared mobile UI and goal cards.
- `src/store`: Zustand actions and serialized SQLite persistence.
- `src/database`: versioned schema and indexes; transactionally saved snapshots with cascading foreign keys.
- `src/utils/domain.ts`: pure progress and timestamp calculations.
- `src/services`: notifications, JSON backup and native state reconciliation.
- `modules/focus-bubble`: Android-only Expo native module, foreground service, overlay manager and Canvas timer.

JS persists accumulated elapsed seconds, wall-clock anchors and deadlines. Kotlin uses `SystemClock.elapsedRealtime` while its service is alive, avoiding device-clock changes during native timing. Native pause/resume/completion is journaled in SharedPreferences and reconciled into SQLite when the app is active. The service intentionally uses `START_NOT_STICKY`; it does not restart itself after reboot. No wake lock or continuous background JavaScript is required. Timer rendering runs once per second.

The first migration creates goal, step, session, preference and achievement tables. Goal/step payloads are versioned by the migration table and currently use JSON columns alongside indexed relational identifiers. Add numbered schema/data migrations before changing persisted shapes. Backups are local JSON files; import validates references and replaces data in a transaction.

## Platform limits and release work

Android overlays can be hidden by secure screens, other apps and manufacturer policies. Revoking overlay permission stops the service; the JS session can still be restored. A stopped service or killed process cannot guarantee a visible bubble. Reboot does not restart it. Across a full process death, wall-clock restoration cannot distinguish manual clock changes from actual elapsed time; negative changes are clamped, and countdowns are capped. Avoid changing the device clock during sessions.

The `specialUse` foreground service is for the explicitly user-started visible overlay; it is not a media, location or data-sync service. Google Play requires a foreground service declaration and review for special-use cases. Approval is not guaranteed. No background or boot receiver starts this service. The foreground notification is supplied by Android even if ordinary notification permission is denied, subject to OS presentation rules.

iOS has the in-app timer and optional local completion alerts. System-wide overlays are unsupported. Live Activities require a separate widget extension and are not implemented. Pomodoro breaks are started explicitly after focus completion. Reminders are daily and skipped when their scheduled hour falls within quiet hours. Focus completion alerts are controlled by the same notification preference.

## Physical-device acceptance checklist

Native overlay behavior must be validated on real hardware; source implementation alone is not proof of device compatibility.

1. Test Android 12, 13, 14, 15 and newer supported releases. Create/edit/delete goals; add, complete, edit and reorder steps. Restart and confirm persistence.
2. Run a short countdown, stopwatch and Pomodoro. Pause/resume repeatedly; background, lock, unlock and reopen. Confirm elapsed time and completed-session history.
3. Grant/deny/revoke overlay permission and notification permission independently. Confirm no permission is requested at onboarding. Enable only from the visible app.
4. Switch to Chrome and other apps. Check ring/countdown, expanded panel, pause/resume, open-app navigation and hide/restore. Verify stopping from native controls updates SQLite after return.
5. Drag to both edges and the dismiss zone. Check saved position, cutouts, gesture/navigation bars, rotation, foldables and display-size changes. The application locks portrait by default; verify resizing in multiwindow.
6. Kill JS while the service runs; change native timer state; reopen. Kill the entire process and restore. Reboot and confirm there is no unsolicited overlay restart.
7. Test Doze, battery saver and manufacturer background restrictions. Check notification fallback and completion reconciliation after OS service termination.
8. Export/import a backup, including malformed files. Test large fonts, TalkBack, reduced motion, light/dark appearance and keyboard visibility.

Automated tests cover domain calculations, native-state reconciliation, backup validation and the actual SQLite schema using Node’s SQLite engine. Kotlin compilation, device lifecycle, drag behavior and cross-app visibility require Android build and device tests. See `IMPLEMENTATION.md` for current verification results and known gaps.

Reference documentation: [Expo SDK 58](https://docs.expo.dev/versions/v58.0.0/), [local native modules](https://docs.expo.dev/modules/get-started/), [Android foreground service types](https://developer.android.com/develop/background-work/services/fgs/service-types).
